| Field | Value |
|---|---|
| Date | 2026-10-23 |
| Component | GATK HaplotypeCaller (germline small variants) |
| From → to | `broadinstitute/gatk:4.6.2.0@sha256:71b17ee42d149e8ec112603f5305c873ab60d93949ef8bb62a4fff85427f56fb` → `broadinstitute/gatk:4.7.0.0@sha256:7da5cf586e1c463f0c72908f9ac7dec8c29e37912c82d6e7b3c250f27fcb3891` |
| Decision | **Approve** |

## Summary and recommendation

Approve. On the 5 Mb `full` profile, GATK 4.7.0.0 produced exactly the same calls as 4.6.2.0:
the 8,799 normalised VCF records are identical byte for byte, including INFO and genotype fields.
No site changed benchmark decision, every stratum's F1 is unchanged, and the regression gate
passes with 0 of 26 rows failing. Runtime is within run-to-run noise.

## What changed

From the [4.7.0.0 release notes](https://github.com/broadinstitute/gatk/releases/tag/4.7.0.0)
(published 2026-08-18), the items that could affect germline calling with HaplotypeCaller:

> Upgraded to **HTSJDK 5.0.0** and **Picard 3.5.0**, bringing full CRAM 3.1 write support and
> faster BAM/CRAM I/O (#9406, #9216).

> Updated **GKL to 0.9.1**, including an optimized implementation of the DRAGEN PDHMM (#9152, #9220).

Under HaplotypeCaller:

> Added a command-line option to upweight ALT-supporting reads (#9234).

> New `--output-cram-version` option to select the CRAM version (3.0 or 3.1) for CRAM output;
> default is 3.1 (#9413).

The read-library upgrade (HTSJDK 5) is the change most likely to matter: it touches every BAM
read. The ALT-upweighting option is new and off unless requested, and this workflow does not use
the DRAGEN PDHMM. The CRAM default affects only tools that write CRAM, which this workflow does
not do.

## Validation performed

- Profile `full`: HG002 35x NovaSeq, `chr20:21000001-26000000` (5 Mb), against GIAB v4.2.1 with
  the GIAB v3.6 stratifications listed in `config/strat_subset.tsv`; hap.py 0.3.15 with vcfeval.
- Both runs used the same inputs, thread counts and memory (4 CPU, 6 GiB); only the image differed.
  Preflight was off for both, since it does not affect calls.

```bash
make run PROFILE=full LABEL=full-gatk-4.6.2.0 EXTRA="run_preflight=false callers=gatk \
    gatk_docker=broadinstitute/gatk:4.6.2.0@sha256:71b17ee42d149e8ec112603f5305c873ab60d93949ef8bb62a4fff85427f56fb"
make run PROFILE=full LABEL=full-gatk-4.7.0.0 EXTRA="run_preflight=false callers=gatk"
python3 scripts/compare_metrics.py docs/results/full-gatk-4.6.2.0/metrics.json \
    docs/results/full-gatk-4.7.0.0/metrics.json --thresholds config/thresholds.yaml \
    --out-md docs/results/full-gatk-4.7.0.0/upgrade-gate.md
python3 scripts/diff_decisions.py results/full-gatk-4.6.2.0/gatk.vcf.gz results/full-gatk-4.7.0.0/gatk.vcf.gz
python3 scripts/plot_metrics.py --metrics 4.6.2.0=docs/results/full-gatk-4.6.2.0/metrics.json \
    --metrics 4.7.0.0=docs/results/full-gatk-4.7.0.0/metrics.json --out docs/results/figures \
    --prefix gatk-upgrade- --title "GATK HaplotypeCaller 4.6.2.0 vs 4.7.0.0, full profile"
```

## Runtime and cost impact

`HaplotypeCaller` rows of `docs/results/<label>/resources.tsv` (one run each, same machine, run
one after the other):

| Version | Wall time (s) | CPU time (s) | Peak memory (bytes) |
|---|---:|---:|---:|
| 4.6.2.0 | 282.75 | 1053.44 | 1,576,427,520 |
| 4.7.0.0 | 288.09 | 1072.01 | 1,448,022,016 |

CPU time is 1.8% higher with 4.7.0.0. One run per version cannot separate a change that small
from noise: on the same laptop, one DeepVariant configuration took 69.5 s in one run and 100.3 s
in another while other containers were busy ([CS-03](../case-studies/CS-03-deepvariant-memory.md)).
Peak memory is the task cgroup's `memory.peak`, which counts page cache; it stays well under the
6 GiB request. No change to the cost estimate.

## Risks and follow-ups

- **Not covered: GVCF mode.** This workflow calls in VCF mode. Customers who joint-genotype run
  HaplotypeCaller with `-ERC GVCF`; validate that path (and GenotypeGVCFs) before telling them
  the upgrade changes nothing.
- **Not covered: CRAM input.** HTSJDK 5 changes CRAM reading and writing. Inputs here are BAM.
  Run one CRAM-input sample before release to customers who send CRAM.
- **Scale.** 5 Mb of one chromosome of one sample. Identical output here makes a genome-wide
  difference unlikely, not impossible.
- After release, watch the weekly `full` CI run for any change against `baselines/full.json`.
